# 架构（当前实现）

> 原则：**一个线程只干一件事；所有点击只有一个出口。**
> 这条不是洁癖，是被实测打出来的：主线一次 OCR 0.5–1.5 s，单线程时弹窗/过场全漏；
> 而多线程各自点又会互相插队。

---

## 1. 三层结构

```
┌──────────────────────────────────────────────────────────────┐
│ L1 采集层  Capture (1 个线程)                                  │
│    GDI BitBlt 抓 MuMu 窗口 → crop 掉 40px chrome → 最新帧槽     │
│    8 Hz，单帧 6–10 ms；不排队，只保留最新（旧帧直接丢）           │
└───────────────────────────┬──────────────────────────────────┘
                            │ latest frame（只读共享）
┌───────────────────────────▼──────────────────────────────────┐
│ L2 决策层  6 个独立 worker（各自节拍，互不阻塞）                 │
│                                                               │
│  skip    6 Hz  ▶▶ 跳过剧情        仅"无 HUD"时（防误点头像）    │
│  close   5 Hz  ✕ 关闭面板         人物属性/福利/任务面板         │
│  use     5 Hz  使用 / 领取        弹窗里的可点按钮               │
│  battle  2 Hz  攻击 + 点目标      战斗中                        │
│  monitor 1 Hz  HP / MP / 等级     只读，不动手                  │
│  quest   1 Hz  追踪条 / 任务面板   主线推进                      │
└───────────────────────────┬──────────────────────────────────┘
                            │ push(优先级, x, y, 标签)
┌───────────────────────────▼──────────────────────────────────┐
│ L3 动作层  Executor (1 个线程，全局唯一 adb tap 出口)            │
│    优先级队列：0 = 中断（skip/close/use）  5 = 主线             │
│    过期丢弃：动作排队 > 1.5 s 就作废（状态早变了）               │
│    单线程串行 → 不会出现"点了 A 又点 B"                         │
└──────────────────────────────────────────────────────────────┘
```

---

## 2. 线程职责表

| 线程 | 频率 | 读什么 | 输出 | 失败时 |
|---|---|---|---|---|
| `Capture` | 8 Hz | MuMu 窗口位图 | latest frame | 黑帧自动降级 PrintWindow；连续失败抛错 |
| `skip` | 6 Hz | ▶▶/手动 模板 + HUD 探测 | `push(0, …)` | 模板不匹配 → 固定坐标 (920,27) |
| `close` | 5 Hz | ✕ 模板（hero_close/hero_close2/panel_close） | `push(0, …)` | 找不到就不动 |
| `use` | 5 Hz | 使用/领取 模板 | `push(0, …)` | 冷却 2 s 防连点 |
| `battle` | 2 Hz | 攻击 + 特技 两个按钮同时存在 | `push(5, 攻击)` → `push(5, 目标)` | 不在战斗就不动 |
| `monitor` | 1 Hz | HP/MP 色条宽度、等级角标 OCR | 日志 + 事件 | 读不到就跳过 |
| `quest` | 1 Hz | 任务按钮 + 追踪条模板 | `push(5, 追踪条目标行)` | 12 s 无动作才触发 |

## 3. 关键竞态处理

| 问题 | 现象 | 解法 |
|---|---|---|
| ▶▶ 模板在主界面也命中 | 一点就点头像 → 打开人物属性 → 关闭 → 再命中（实测 40 次循环） | **HUD 门控**：`skip` 先查有没有任务/好友按钮，有就不点 |
| 多线程同时点 | 中途互相插队 | 所有动作进 `Executor` 单队列串行执行 |
| 动作过期 | 排队 1.5 s 后才执行，界面已变 | 入队时间戳超过 1.5 s 直接丢弃 |
| 面板 vs 主界面判定 | 模板时而命中时而失配（开合动画） | worker 用"独立特征"判定，不共用一个 state 变量 |
| OCR 慢堵住全流程 | 弹窗等 1.5 s 才被看见 | OCR 只在 `quest`/`monitor` 里用，其余 worker 纯模板 |

---

## 4. 安全闸门

- `quest.ACTIONS_ENABLED` 默认 **False**：任何 `adb_tap` 都会抛 `ActionsDisabled`
- 三个入口都必须显式加 `--enable-actions`
- `Executor` 是唯一真调 `adb tap` 的地方 → 审计只需看这一个函数

## 5. 实测数据（本机 i5-10400 + MuMu NX15，960×540）

| 项 | 数值 |
|---|---|
| 抓帧（GDI BitBlt） | 6–10 ms（被遮挡仍有效；最小化无效） |
| 单模板匹配（小模板） | 1–3 ms |
| 键鼠注入 | `PostMessage` <1 ms（键盘有效，鼠标无效）；`adb input tap` 74–153 ms |
| 单实例 CPU（8 Hz 采集 + 6 worker） | ≈0.3 核；4 开 ≈1.2 核 |
| 面板 OCR（标题/目标） | 0.6–2.9 s（首次含模型加载） |
| 等级角标 OCR | ~0.3 s（4 倍放大） |

## 6. 怎么加一个新 worker（示例：NPC 名字搜索）

```python
class NpcWorker(BaseWorker):
    name_, hz = "npc", 1.0

    def step(self):
        f = self.frame()
        if f is None:
            return
        # 只在自己的目标上下文里干活：例如追踪条写着"劝说父子俩"
        hits = self._ocr_name_tags(f)          # 复用人脸/名字条检测
        for txt, (cx, cy) in hits:
            if txt in ("父亲", "儿子"):
                self.ex.push(5, cx, cy, "npc:click")
                self.say(f"找到 {txt} @({cx},{cy})")
                return
```

然后在 `Fleet.start()` 里 `fleet.workers.append(NpcWorker(cap, ex))`。
**不需要改任何其它线程** —— 这就是拆开的好处。

## 7. 已知缺口

1. **NPC 名字搜索**（劝说父子俩这一环需要）——见 §6 模板
2. **对话选项**（"请选择要做的事"）目前靠 OCR「对话/继续」命中，还没做成独立 worker
3. **战斗策略**：现在只会普攻 + 点第一个目标；需要"用技能/捕捉/逃跑"时得加规则
4. **追踪条文字变化检测**：小字号 OCR 不稳，目前只用于"有没有变化"，不解析语义
5. **多实例**：6 个 worker 的模板/ROI 都是单实例基准，多开时每个实例要独立 `Capture` + `Fleet`
